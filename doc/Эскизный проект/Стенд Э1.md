## Проверка узла KVM

На согласованном узле Linux под учётной записью агента выполнить проверки ниже. `virsh` следует запускать без `sudo`, чтобы проверить права этой учётной записи. Команды проверяют конфигурацию и читают состояние узла.

```bash
uname -m
cat /etc/os-release
id
grep -m 1 -E '^flags[[:space:]]*:.*[[:space:]](vmx|svm)([[:space:]]|$)' /proc/cpuinfo
ls -l /dev/kvm
virt-host-validate qemu
virsh -c qemu:///system version
virsh -c qemu:///system list --all
virsh -c qemu:///system domcapabilities --virttype kvm --arch x86_64
virsh -c qemu:///system net-list --all
```

Зафиксировать дистрибутив, архитектуру `x86_64`, версии libvirt и QEMU, результаты проверки аппаратной виртуализации и доступ к `qemu:///system`. Выбрать действующую сеть libvirt и зафиксировать её имя в конфигурации узла. Создание домена и доступ QEMU к файлам гостя проверяются при прогоне Э4.

На узле зафиксировать идентификатор `imageId` в формате UUID, путь к образу, дистрибутив и архитектуру гостя, источник, условия использования и опубликованную SHA-256. Указать путь и ожидаемую SHA-256 до запуска команд.

```bash
qemu-img info --output=json "$guest_image"
test -r "$guest_image"
printf '%s  %s\n' "$guest_sha256" "$guest_image" | sha256sum --check
df -h -- "$guest_image"
```

В метаданных диска проверить формат `qcow2`, размер и наличие родительского файла. При наличии родительского файла также проверить его доступность и происхождение. Архитектуру и режим загрузки получить из документации образа, затем подтвердить загрузку в Э4. На файловой системе узла предусмотреть место для диска тестовой ВМ.

## Связь и источники пакетов

Агент с назначенным `nodeId` подключается исходящим соединением к HTTPS-адресу службы управления ВМ с взаимной аутентификацией TLS. Для макета предусмотрен TCP 8443 на сервере управления. PostgreSQL и шина находятся на стороне сервера управления. Входящее подключение к агенту для заявки на создание ВМ не требуется.

На узле зафиксировать разрешение имени сервера управления, доступность TCP 8443 и ограничения межсетевого экрана. После запуска службы проверить TLS-рукопожатие, указав имя сервера и пути к доверенному сертификату, клиентскому сертификату и ключу агента.

```bash
getent ahosts "$management_host"
openssl s_client -connect "${management_host}:8443" -servername "$management_host" \
  -verify_hostname "$management_host" -verify_return_error -min_protocol TLSv1.2 \
  -CAfile "$management_ca" -cert "$agent_certificate" -key "$agent_key" -brief < /dev/null
```

- На сервере управления подтвердить доступ к репозиторию Maven и реестру с выбранными версиями образов PostgreSQL и шины. Записать адрес зеркала или реестра и способ доступа без учётных данных.
- На узле согласовать официальное хранилище пакетов выбранного дистрибутива или его зеркало. Для сборки и проверки агента учесть GCC, CMake, заголовки и утилиты libvirt, QEMU. Проверить доступ к ним через настроенный менеджер пакетов.
- К испытаниям подготовить OCI-реестр с проверочным образом для x86-64 и ARM64, например `docker.io/library/alpine` с зафиксированной версией, и пример установки из пакетного хранилища, например `nginx`. Доступность образа и пакета проверяется на целевых узлах.
