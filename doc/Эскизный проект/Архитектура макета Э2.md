# Архитектура и контракт макета KVM

Макет выполняет одну операцию: создаёт и запускает ВМ из подготовленного образа на явно указанном узле Linux x86-64 с KVM/libvirt. Состав макета определён в § 6.5 ТЗ v2. Контракты HTTP описаны для [службы оркестрации](../../api/orchestrator.openapi.yaml) и [службы управления ВМ](../../api/vm-service.openapi.yaml). Проверки стенда вынесены в [инвентаризацию Э1](Стенд%20Э1.md).

## Владельцы данных

Каждая служба с собственными данными использует отдельную схему PostgreSQL и работает с данными других служб через их API или сообщения. В макете разворачиваются схемы `orchestrator` и `vm_service`.

| Компонент | Данные и ответственность |
| --- | --- |
| Шлюз | Маршрутизация, первичная проверка токена и ограничение частоты запросов. |
| Служба авторизации | Пользователи, проекты, роли, права, токены и учётные данные агентов. |
| Служба инвентаризации | Идентификаторы узлов, характеристики, платформы, метки, ресурсы и параметры подключения. |
| Служба каталога | Метаданные образов ВМ, ссылки на OCI-образы, версии YAML-шаблонов и сценарии установки. Файлы образов ВМ хранятся отдельно. |
| Служба оркестрации | Заявка, выбранный узел, шаги, статус, ссылки на результаты и задания на публикацию. |
| Служба управления ВМ | Команды агенту, результаты выполнения, требуемое и фактическое состояние ВМ. |
| Служба управления контейнерами | Требуемое и фактическое состояние контейнеров. |
| Служба развёртывания ПО | Требуемое и фактическое состояние ПО, включая установленные версии. |
| Служба-адаптер Windows | Исполнение операций WinRM и передача результатов службам-владельцам. |
| Служба наблюдения | Наблюдения, события, аудит, уведомления и выявленные расхождения. |
| Агент узла | Данные о фактическом состоянии узла и выполнение операций через платформу. |

## Путь заявки и хранение состояния

1. В системе пользователь подаёт заявку через шлюз, который проверяет токен и передаёт запрос в службу оркестрации. В макете клиент обращается напрямую к локальному API службы оркестрации. Пользователь указывает узел и образ, подготовленные на стенде.
2. `POST /api/v1/requests` присваивает заявке и шагу разные UUID и одной транзакцией сохраняет параметры, шаг в состоянии `QUEUED` и запись для публикации. После фиксации транзакции API отвечает `202 Accepted` и указывает в `Location` адрес чтения состояния заявки.
3. Служба оркестрации публикует JSON-команду `vm.create` в очередь RabbitMQ `prototype.vm.create.v1`. Служба управления ВМ сохраняет команду с уникальным `stepId` в своей схеме и подтверждает доставку после фиксации транзакции.
4. Агент устанавливает исходящее HTTPS-соединение и опрашивает службу управления ВМ. После выдачи команды служба временно резервирует её за агентом. Если соединение потеряно и резерв истёк, повторная выдача сохраняет `stepId` и параметры команды.
5. Агент получает путь к базовому образу по `imageId` из конфигурации узла, создаёт отдельный системный диск, определяет конфигурацию ВМ и запускает её через C API libvirt. Базовый образ доступен только для чтения. Для поиска ВМ после потери ответа её UUID равен `stepId`. Перед повтором агент сверяет конфигурацию существующей ВМ с командой и возвращает конфликт при расхождении.
6. Агент передаёт результат в службу управления ВМ. Служба атомарно сохраняет итог команды и запись для публикации результата в очередь `prototype.vm.result.v1`. Служба оркестрации сопоставляет результат с заявкой и шагом, сохраняет итог и подтверждает сообщение. `GET /api/v1/requests/{requestId}` читает сохранённое состояние.

| Схема | Таблицы макета | Ключи и ограничения |
| --- | --- | --- |
| `orchestrator` | Заявки, шаги, задания на публикацию | UUID заявки и шага, один шаг на заявку, ссылка задания публикации на шаг. Результат относится к сохранённой заявке и шагу. |
| `vm_service` | Команды, ВМ, результаты на публикацию | `stepId` уникален для команды. Для ВМ сохраняются узел, UUID libvirt, параметры и состояние. Один итоговый результат на шаг. |

RabbitMQ доставляет сообщения как минимум один раз. Очереди и сообщения сохраняются на диске. Издатель отмечает задание как отправленное после подтверждения от RabbitMQ и проверяет, что сообщение попало в очередь. Исполнитель и оркестратор распознают повторы по `stepId`, принимают совпадающее сообщение повторно и регистрируют расхождение при конфликте. Сбой транспорта не меняет итоговое состояние на `FAILED`. Политики длительности резерва, повторов, отмены и дальнейшей сверки уточняются в Т3.

## Формат заявки и результата

В заявке обязательны `nodeId`, `imageId`, `name`, `vcpus`, `memoryMiB`, `diskGiB` и `network`. Первые два поля — UUID. Имя ВМ и имя сети — строчные ASCII-буквы, цифры и внутренние дефисы в пределах 1–63 символов. Числовые поля задают число виртуальных ЦП, память в МиБ и целевой размер единственного системного диска в ГиБ. Служба проверяет формат запроса, а агент проверяет, что образ и сеть утверждены для узла и размер диска не меньше виртуального размера образа. Первичная настройка гостевой ОС, автоподбор узла и дополнительные диски относятся к следующим работам.

Сообщение команды содержит те же параметры и поля `schemaVersion: 1`, `operation: vm.create`, `requestId` и `stepId`. Сообщение результата повторяет версию, операцию, идентификаторы заявки, шага и узла. Результат `SUCCEEDED` содержит `result.vmId` после запуска ВМ. Результат `FAILED` содержит `error` с кодом, объектом, именем шага `VM_CREATE` и описанием причины на русском языке. Ошибка проверки запроса возвращается с HTTP 400, обращение к отсутствующей заявке — с HTTP 404. Структуры команд и результатов заданы в [схемах JSON](../../api/schemas.yaml).

## Подключение агента

Порт HTTPS для исходящего подключения агента — TCP 8443 на сервере управления. Служба и агент проверяют сертификат второй стороны по доверенному центру и требуют TLS 1.2 или выше. Агент проверяет имя сервера. Служба привязывает сертификат клиента к `nodeId`, выдаёт только его команды и принимает только результаты его шагов. Конфигурация узла ограничивает перечень разрешённых образов и сетей libvirt. Команда несёт идентификаторы, разрешённое имя и параметры ресурсов.

Для макета сертификаты и привязку узла подготавливает оператор стенда. Автоматическая регистрация, отзыв учётных данных и совместимость версий относятся к Т5 и Р4. Агент реализует защищённое соединение и вызовы libvirt в Э4. Пригодность TLS-библиотеки и способ поставки агента с libvirt проверяются в Т6.

## Набросок единого шаблона YAML

Версия шаблона фиксируется для каждой заявки. Тип шага определяет параметры `with`. Поле `needs` перечисляет идентификаторы шагов, результаты которых требуются для запуска. Для макета показан один шаг. Поддержка чтения шаблона и ссылок на результаты проектируется в Т1.

```yaml
apiVersion: orchestration/v1
kind: DeploymentTemplate
metadata:
  name: kvm-guest
  version: 1
spec:
  steps:
    - id: guest
      type: vm.create
      needs: []
      with:
        nodeId: 14c48a31-e5a4-491b-8f96-6a82876afa95
        imageId: 6b7cda20-f659-479c-b30f-fb3913da97b6
        name: demo-guest
        vcpus: 2
        memoryMiB: 2048
        diskGiB: 20
        network: default
```

## Границы реализации

Э3 готовит запуск служб, приём и чтение сохранённой заявки, окружение PostgreSQL и RabbitMQ и сборку агента. Э4 проверяет передачу команды агенту, запуск гостя на KVM и получение результата. Э5 подтверждает путь через очередь, сохранность итогов после перезапуска и воспроизводимость полного сценария.
